1.1 · 从 Kernel 启动到 CU ​

CPU 启动一个 Kernel 后，DCU 会把这次计算的 Block 分派到计算单元（CU）执行。本章用一次向量加法说明任务是怎么拆分和分派的。

基础概念 · 软件模型与硬件资源 ​

理解 DCU 微架构，首先要区分两个概念：

  • 软件执行模型： 程序员如何组织线程、划分计算任务。
  • 硬件执行架构： GPU 如何分配计算资源、调度线程、执行指令和搬运数据。

二者相互关联，但不是简单的一一对应关系。

1.1 软件执行模型 ​

在 HIP 编程中，一次 Kernel 启动会形成一个 Grid，Grid 包含多个 Block（Workgroup），每个 Block 内包含多个 Thread（Work-item）。

以 Wavefront Size 为 64、Block Size 为 256 为例：

text
Kernel Launch
│
└── Grid
    │
    ├── Block 0（256 Threads）
    │   ├── Wavefront 0（Thread 0～63）
    │   ├── Wavefront 1（Thread 64～127）
    │   ├── Wavefront 2（Thread 128～191）
    │   └── Wavefront 3（Thread 192～255）
    │
    ├── Block 1（256 Threads）
    │   └── 4 个 Wavefront
    │
    └── Block N
        └── 4 个 Wavefront

各层级的职责如下：

概念主要作用与硬件的关系
Grid组织一次 Kernel 的全部计算任务分布到整张 GPU 的多个 CU
Block / Workgroup组织可以共享数据并同步的线程一个 Block 被分配到一个 CU
Wavefront一组共享指令执行流的线程GPU 的重要调度与执行单位
Thread / Work-item同一个概念的两种叫法，指执行一份 Kernel 代码的逻辑线程每个线程在所属 wave 中占一个逻辑 lane
Lane一个线程在所属 wave 里的位置，编号从 0 开始lane 编号只在该 wave 内有意义，可以用于执行掩码或跨 lane 通信

以 Wave64 为例，同一 Block 内 threadIdx.x = 0 的线程是 Wave 0 的 Lane 0，threadIdx.x = 64 的线程是 Wave 1 的 Lane 0。它们是两个不同的线程，只是在各自 wave 里的位置相同。Grid、Block、wave 和线程描述的是程序怎样组织执行，承载这些工作的是 CU 等硬件资源。

主线案例 · 1000 个元素的向量加法 ​

本部分始终跟着 C[i] = A[i] + B[i] 走一遍。Host 提交一次 Kernel。我们设 N=1000、每 Block 256 个线程，使用 BW100 的 Wave64 举例。

Grid、Block 和 wave 哪些可以设置？ ​

启动 Kernel 时，程序员可以直接设置 Grid 有多少个 Block，也可以设置 每个 Block 有多少个线程。下面是本例的一维启动配置：

cpp
// 依次指定 Grid 的 Block 数、每个 Block 的线程数。
// 接下来的两个 0 表示不额外申请动态 LDS、使用默认 stream。
hipLaunchKernelGGL(tutorial_add, dim3(4), dim3(256), 0, 0,
                   device_a, device_b, device_c, 1000);
数量怎么得到本例
Grid 中的 Block 数启动时直接传入，Kernel 内可用 gridDim.x 查看dim3(4)
每个 Block 的线程数启动时直接传入，Kernel 内可用 blockDim.x 查看dim3(256)
每个 wave 的 lane 数由目标设备的执行模式决定，可查询设备的 warpSize本例的 BW100 为 64
每个 Block 的 wave 数用 Block 的线程总数除以 wave 宽度，向上取整ceil(256 / 64) = 4

因此，可以通过调整 Block 的线程数来改变每个 Block 的 wave 数。普通 HIP launch 没有单独设置 wave 数或把 BW100 的 Wave64 改成其他宽度的参数。本例中，一个线程负责一个元素，所以在选定 256 线程后，程序用 ceil(1000 / 256) = 4 算出够用的 Block 数。最后一个 Block 多出来的线程由边界检查挡住。

线程怎么找到自己要算的元素？ ​

cpp
// 将 Block 编号和 Block 内的线程编号合成全局索引。
const int i = blockIdx.x * blockDim.x + threadIdx.x;
// 4 × 256 个线程覆盖 1000 个元素，越界线程跳过读写。
if (i < count) {
    c[i] = a[i] + b[i];
}

这里的「驻留」是指 Block 已被分配到某个 CU，并占用执行所需的硬件资源。两个 Block 即使驻留在同一个 CU，也各有自己的 Block 内同步范围。

按一维索引展开，Block 3 对应 i=768–1023，前三个 wave 负责 192 个完整元素，最后一个 wave 覆盖 960–1023。其中 40 个元素在范围内，剩下 24 个线程走边界检查，任何一个 Block 分到哪个 CU、何时运行都由设备决定。即使 BW100 有 64 个 CU，本例也只提交了 4 个 Block。

一次 launch 怎么结束 ​

  1. 提交　Host 端 HIP Runtime 接到 launch 配置和参数。普通 launch 可以异步返回给 Host。
  2. 分发　设备把就绪的 Block 分配到有足够资源的 CU。同一 Block 的 wave 在同一个 CU 上执行。
  3. 执行　CU 调度器选择就绪 wave 发射指令。每个有效线程读取 A 和 B，计算后写入 C。
  4. 完成　一个 Block 做完后释放驻留资源。全部 Block 完成，Host 可以通过同步或事件观察任务结束。

这里用的是通用 HIP 编程模型，Wave64 和设备参数以 BW100 实测基线 为例。z100 的功能结构与 HSA 软件栈在下方进阶阅读。通用层级也可参照 HIP 编程模型。

动手运行 ​

在仓库根目录运行。换卡时通过设备属性确认编译目标和 wave size。

bash
cd experiments
hipcc -O3 -std=c++17 --offload-arch=gfx936 -save-temps vector_add_tutorial.hip -o tutorial_add
./tutorial_add

BW100 运行结果 ​

text
BW100 gfx936:sramecc+:xnack- | 4 blocks x 256 threads | wave size 64 | 1000 outputs verified, 24 untouched

设备报告的 wave 宽度是 64。程序在 CPU 上逐项检查输出，确认 1000 个有效结果正确，多启动的 24 个线程没有改动输出数组末尾的初始值。

什么是设备端 ISA？ ​

ISA 是「指令集架构」，可以理解为一份规则，规定硬件认识哪些指令，以及每条指令做什么。这里的设备端指执行 Kernel 的 DCU。编译器会把 HIP C++ 写的 Kernel 翻译成它能执行的机器指令。

-save-temps 会保留设备端的 .s 汇编文件，方便人读这些指令。例如，C++ 的一行 c[i] = a[i] + b[i] 会对应读入 A 和 B、等待数据、做加法、写回结果等步骤。第 1.3 章会展示本例实际生成的片段。

查看完整 HIP 示例
cpp
#include "common.h"

#include <vector>

__global__ void tutorial_add(const float* a, const float* b, float* c, int count) {
    // blockIdx.x 决定这个 Block 的起始位置，threadIdx.x 给出线程在块内的偏移。
    const int i = blockIdx.x * blockDim.x + threadIdx.x;
    // 最后一个 Block 有多余线程，只让有效索引读写数组。
    if (i < count) {
        c[i] = a[i] + b[i];
    }
    return;
}

int main() {
    constexpr int count = 1000;
    constexpr int threads = 256;
    // 向上取整，让 Grid 覆盖全部元素。1000 个元素需要 4 个 Block。
    constexpr int blocks = (count + threads - 1) / threads;
    constexpr float untouched = -1.0f;

    // 输出数组预留到启动线程总数，并填入初始值，用来检查尾部没有被误写。
    std::vector<float> a(count), b(count), c(blocks * threads, untouched);
    for (int i = 0; i < count; ++i) {
        a[i] = static_cast<float>(i);
        b[i] = static_cast<float>(2 * i);
    }

    // Host 上的数组先复制到 DCU 可访问的设备内存。
    float *device_a = nullptr, *device_b = nullptr, *device_c = nullptr;
    const size_t input_bytes = a.size() * sizeof(float);
    const size_t output_bytes = c.size() * sizeof(float);
    HIP_CHECK(hipMalloc(&device_a, input_bytes));
    HIP_CHECK(hipMalloc(&device_b, input_bytes));
    HIP_CHECK(hipMalloc(&device_c, output_bytes));
    HIP_CHECK(hipMemcpy(device_a, a.data(), input_bytes, hipMemcpyHostToDevice));
    HIP_CHECK(hipMemcpy(device_b, b.data(), input_bytes, hipMemcpyHostToDevice));
    HIP_CHECK(hipMemcpy(device_c, c.data(), output_bytes, hipMemcpyHostToDevice));

    // 启动参数指定 Grid 的 Block 数和每个 Block 的线程数。
    // 两个 0 分别表示不额外申请动态 LDS、使用默认 stream。
    hipLaunchKernelGGL(tutorial_add, dim3(blocks), dim3(threads), 0, 0,
                       device_a, device_b, device_c, count);
    HIP_CHECK(hipGetLastError());
    // Host 等待 Kernel 执行完成，再把结果复制回 CPU 检查。
    HIP_CHECK(hipDeviceSynchronize());
    HIP_CHECK(hipMemcpy(c.data(), device_c, output_bytes, hipMemcpyDeviceToHost));
    HIP_CHECK(hipFree(device_c));
    HIP_CHECK(hipFree(device_b));
    HIP_CHECK(hipFree(device_a));

    // 有效位置必须等于 CPU 算出的和，尾部的初始值必须保持原样。
    for (int i = 0; i < blocks * threads; ++i) {
        const float expected = i < count ? a[i] + b[i] : untouched;
        if (c[i] != expected) {
            std::fprintf(stderr, "Mismatch at output index %d\n", i);
            return EXIT_FAILURE;
        }
    }
    // wave 宽度从设备属性查询，本例没有在 launch 时设置它。
    hipDeviceProp_t device{};
    HIP_CHECK(hipGetDeviceProperties(&device, 0));
    std::printf("%s %s | %d blocks x %d threads | wave size %d | %d outputs verified, %d untouched\n",
                device.name, device.gcnArchName, blocks, threads, device.warpSize, count,
                blocks * threads - count);
}
复述题 · 保持 N=1000，每 Block 改成 128 个线程，需要几个 Block？

沿用本例「一个线程算一个元素」的写法，Grid 需要 8 个 Block（ceil(1000 / 128)）。在 BW100 的 Wave64 下，每个 Block 有 2 个 wave。最后一个 Block 从索引 896 开始，有 104 个有效线程，其中最后一个 wave 有 40 个有效线程。

1.2 DCU 的物理硬件组织 ​

以早期 z100 类微架构为例，可以建立如下整体认知：

text
DCU GPU
│
├── 命令处理与任务分发
│   ├── 接收 Kernel Dispatch
│   ├── 管理计算任务
│   └── 将 Workgroup 分配给 CU
│
├── Compute Unit 0
│   │
│   ├── 调度与控制单元
│   │   ├── Wavefront Scheduler
│   │   ├── 指令发射与依赖管理
│   │   └── 分支与执行掩码控制
│   │
│   ├── Scalar 执行资源
│   │   ├── SALU
│   │   └── SGPR
│   │
│   ├── Vector 执行资源
│   │   ├── SIMD 0 + VGPR
│   │   ├── SIMD 1 + VGPR
│   │   ├── SIMD 2 + VGPR
│   │   └── SIMD 3 + VGPR
│   │
│   ├── 矩阵乘加功能
│   │   └── MMAC / 矩阵乘加指令路径
│   │
│   ├── LDS（片上共享存储）
│   │
│   └── 访存接口与近端 Cache
│
├── Compute Unit 1
│   └── ...
│
├── Compute Unit N
│   └── ...
│
├── GPU 片上互连与共享 L2 Cache
│
└── Memory Controller
    └── HBM / 全局显存

这是一张逻辑功能结构图，不是具体芯片的物理布局图。

例如矩阵计算资源可能与 SIMD/向量执行资源存在复杂的共享关系；L1、L2 的实际组织与共享范围也因芯片代际而不同。

图中 z100 的部分特性，包括每 CU 四组 SIMD、Wave64 和 CU 内共享 LDS，可以作为学习起点，但不能直接推断所有 BW 系列采用完全相同的组织方式。

1.3 从 PyTorch 到 DCU 硬件的软件栈链路 ​

参考 hello-rocm 中“解密 AI 加速器（decode-ai-accelerator）”的视角，在实际大模型推理/训练中，一条算子调用是如何穿透软件栈到达上述物理硬件的？

text
PyTorch / vLLM / SGLang（计算图与调度）
        │
        ├── 通用数学库：rocBLAS / hipBLAS / MIOpen
        ├── 高级融合算子库：lightop / aiter / deepgemm
        └── DSL 编译器：Triton（Python → TTIR → TTGIR → LLVM IR → AMDGCN ISA）
                ↓
        HIP / DTK Runtime（hipLaunchKernelGGL / Stream / Event）
                ↓
        HSA Runtime（用户态队列 AQL Packet、内存管理与信号量）
                ↓
        队列提交（写入 dispatch packet，通知设备有新工作）
                ↓
        DCU Command Processor (CP) → 分发 Workgroup 到各个 CU

这是常见路径示意。驱动为 Runtime 提供设备、队列与内存支持，门铃的具体提交方式取决于平台实现。

理解这条链路有三个直接价值：

  1. 定位“到底跑了谁的 Kernel”：在 PyTorch 中调用一次线性层或 RMSNorm，底层可能走 rocBLAS（Cijk_...）、Triton 生成的 .hsaco、或者 lightop/aiter/deepgemm 的手写/模板 Kernel，用 torch.profiler 或 rocprof 才能看清真实落点。
  2. 理解 Triton 与手写 HIP 的映射关系：Triton 的 tl.load / tl.dot / num_warps / num_stages 并不是魔法，最终都会被 LLVM 后端编译为同样受 VGPR、LDS、s_waitcnt 和 MMAC 约束的设备端 ISA。
  3. 追踪环境依赖：通过 ldd 或 Python 包路径检查 torch 链接的 libamdhip64.so / libhsa-runtime64.so，可以快速排查版本错配或算子回退问题。
